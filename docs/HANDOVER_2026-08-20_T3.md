# Handover — 2026-08-20 · v2.50.0 — T3: the Trade Terminal runs the whole paper loop

**The product promise, wired.** In v2.49.0 (T1) the terminal showed a
professional *layout* but Confirm only sized and toasts. In v2.50.0
(T3) the Confirm button runs the **existing desk path** end to end —
ticket → scan → fresh server-side gate → APPROVED → paper-runner
position under the chart → live R / MAE / MFE / management → Close
records the outcome → journal drawer opens automatically. The complete
experience from `ROADMAP.md` §6 now runs in one screen:

> **chart → understand → paper trade → manage → close → journal.**

**No new trading capability.** Every mutation reuses the existing desk
surfaces: `SignalDB.save_scan` (ticket becomes a real PENDING_REVIEW
scan), `brain.risk_gate.evaluate` (fresh read immediately before the
decision), `update_status` lifecycle decisions (same audit trail),
`data.paper_trading.PaperTradingRunner` (enroll + fill + SL/TP), and
`/api/journal` (the same form the dashboard posts). No threshold moved,
no exchange-order path, no new permission.

## What shipped

### Backend (`web/app.py`)

**`POST /api/terminal/confirm`** — the terminal Confirm. Operator-gated
like every other mutation (default role map; CSRF applies under auth).

1. **Fail-closed validation.** action ∈ {BUY, SELL}; ticket_type ∈
   {market, limit, conditional}; entry/stop positive; stop on the right
   side of entry; `risk_pct ∈ (0, 100]` (an explicit `0` is rejected —
   the original `or 0.5` fallback would have swallowed it); take
   profits numeric and strictly increasing. Invalid tickets persist
   nothing.
2. **A real scan row.** The ticket becomes an engine-shaped payload
   (`signal` with `signal_type=SIGNAL`, one `plan`, snapshot features,
   optional sentiment copied from the chart the human confirmed) and is
   persisted with `db.save_scan` → PENDING_REVIEW. It shows up in
   `/api/pending` like any desk scan, and a gate-blocked confirm leaves
   it there as a genuine review candidate.
3. **Idempotency.** The client sends a `ticket_id`; the scan's
   `signal_id` is `terminal_<ticket_id>`. A retried confirm reuses the
   same scan (200 `duplicate:true`) instead of enrolling a second
   position. A ticket whose scan already reached a terminal state
   answers 409 “ticket already used”.
4. **Fresh server-side gate read immediately before the decision** —
   `gate_evaluate(db, symbol, plan_type, action)` with the ticket's own
   plan type. Blocked → 409 with `blocked_by` and `force_available`
   (identical shape to `/api/review`). `force` requires the same
   `SKY_ALLOW_FORCE_APPROVE` opt-in and is audited; a forced approval
   still will not be *enrolled* while the runner's own gate is shut
   (GATE_BLOCKED event) — exactly the desk force semantics.
5. **Journal-first discipline (W3.3)** — `missing_journals` runs before
   APPROVED, same fail-closed population and same audited
   `acknowledge_journal` escape as `/api/review`.
6. **Enroll + fill.** `PaperTradingRunner.run_once(symbol)` after the
   APPROVED decision: market tickets paper-fill at the confirmed entry
   (scan → EXECUTED), limit/conditional tickets become `WAITING_ENTRY`
   until the level trades, like any conditional desk plan.
7. Response: `{ok, scan_id, status, gate{allowed, blocked_by},
   paper_trade (full row), run}` — the client can tell the human
   honestly whether the runner already filled or even closed the
   position against live candles.

**`POST /api/terminal/close`** — the terminal Close Position.

1. `trade_id` required; unknown → 404; already closed/cancelled → 409
   with the real status.
2. **WAITING_ENTRY** positions are cancelled honestly (nothing traded,
   nothing journaled); scan APPROVED → SKIPPED.
3. **OPEN** positions close with the real economic outcome recorded in
   the existing `TP_HIT` / `STOP_LOSS` buckets — the populations every
   discipline surface already counts (win-rate, `discipline_rows` /
   journal gate, `setup_stats`, calibrator). `close_reason` always says
   `manual terminal close …` with the exact exit, and the decision note
   records the R — the bucket is the win/loss classification, the
   reason is the audit truth. Outcome mapping: at/through target →
   TP_HIT, at/through stop → STOP_LOSS, profit before target → TP_HIT,
   loss before stop → STOP_LOSS.
4. Exit price: explicit `exit_price`, else the runner's `last_price`,
   else the latest candle close; if none is available the close refuses
   (409) rather than inventing a price.
5. Lifecycle: EXECUTED → CLOSED; a trade the runner never advanced past
   APPROVED is advanced honestly (EXECUTED “fill at entry” then CLOSED).
   Lifecycle races (runner closed it concurrently) answer 409.
6. Response: `{ok, trade_id, scan_id, status, outcome, exit_price,
   rr_achieved, journal_required}` — `journal_required` is what makes
   the client open the journal drawer.

### Frontend (terminal section of the served `web/app.py` script;
`web/static/terminal_newjs.js` kept in sync)

- **Ticket** — Confirm posts the full ticket (`ticket_id`, side, type,
  entry, SL, TPs, risk %, plan type, confidence, reason, sentiment).
  The id is reused across retries of the same untouched ticket and
  regenerated when any field changes. A server gate block paints the
  real `blocked_by` verdict into the ticket; the journal block offers
  the same audited acknowledge dialog as the dashboard; success toasts
  honestly (“position open”, “waiting for entry”, or “filled and
  already closed by the runner — journal it below”). The ticket gate
  box now carries a **live** `/api/risk` read (`loadTicketGate`) plus
  the preview from the last scan, both labeled as previews — the
  authoritative read is server-side at confirm.
- **Open positions tab** — reads `/api/trades` (the same live-open book
  and live R the Trade Manager uses) instead of the old empty
  `/api/paper` shapes: #, symbol, side, entry, SL, TP, current, live R,
  MAE / MFE, status, and a per-row **Close** button. Clicking a row
  opens an inline management card: live R / MAE / MFE / minutes in
  trade, entry/stop/target/current, the desk management checklist, and
  **Close Position**. `refreshBottomTab()` re-fetches after confirm and
  close, and the 60 s terminal refresh keeps the visible tab live.
- **Journal tab** — after a close, `_journalTarget` switches the tab to
  the journal and paints an inline form: the recorded outcome and R, a
  Yes/No “did you follow your system” (the headline W3.3 field), an
  emotion selector, mistake and notes — posting to the existing
  `POST /api/journal`. Saving clears the target and refreshes the list;
  an already-journaled trade renders no duplicate form.
- The watchlist position chip (`loadTerminalPositions`) reads the same
  `/api/trades` live book.

## Honest boundaries (unchanged)

- Paper-only. No exchange-order path exists or was added.
- The risk gate, graduation bar, `/api/v1`, auth/roles/CSRF, jobs/SSE,
  and PWA are untouched — T3 calls the same handlers the dashboard
  calls.
- `discipline_rows` (journal gate + graduation discipline) and the
  scorecard populations count manually closed trades exactly because
  they reuse the `TP_HIT` / `STOP_LOSS` vocabulary; nothing was added
  to those populations that wasn't a real decided trade.
- DEMO_MODE honestly simulates: a market ticket at levels far from the
  demo price is filled and immediately stopped by the runner — the UI
  reports it as such instead of pretending the position is open.
- No real browser exists in this sandbox: the UI was proven with the
  node/jsdom harness (`tests/test_terminal_js.py`), the Flask test
  client (`tests/test_terminal_t3.py`), and `curl`-style probes.
  **Visual QA of the T3 loop on a real host is still owed.**
